--- layout: default nav: results exp: e11 title: Interlock Experiment E11 description: "Interlock experiment E11: pre-registered head-to-heads against Shepherd with real Claude Code agents. With all agents on one machine, every Interlock version since V3.9.2 finished 60 of 60 runs on each set it was judged on (6 judged runs, 4 codebases, Claude Haiku 5.5). With each agent on its own simulated machine, V3.16.0 fell short on set R, V3.17.0 won set Q, 54/60 against Shepherd 38/60, and V3.18.0 won set P, 60/60 against 37/60. Earlier versions lost or fell short, and on Sonnet 5.5 the gap was small. Every run is listed." ---

Interlock · Experiment E11실험 E11

Interlock against Shepherd, pre-registeredInterlock 대 Shepherd, 사전 등록 비교

Real Claude Code agents work in parallel on a small codebase. We measure the share of tasks that end correctly merged and passing checks the agents never saw. Each time we changed Interlock after seeing results, we committed a new set of scenarios before running it. Earlier versions lost; the tables list every run, including the ones we set aside.실제 Claude Code 에이전트들이 작은 코드베이스에서 동시에 일합니다. 끝까지 올바르게 병합되고 에이전트가 보지 못한 검사까지 통과한 작업의 비율을 잽니다. 결과를 보고 Interlock을 고칠 때마다, 실행 전에 새 시나리오 세트를 커밋(사전 등록)한 뒤 다시 쟀습니다. 이전 버전은 졌고, 표에는 따로 분류한 실행까지 모든 실행을 실었습니다.

V3.17.0 on set Q, each agent on its own machine세트 Q의 V3.17.0, 에이전트마다 다른 기계

Six scenarios on a parking codebase (90 lines of Python), 10 runs each per condition, 180 runs in all, pre-registered before the run on 2026-10-28; no tool had run on set Q before. Each checkout had its own machine name and Interlock home, and a bare repository played the team’s git remote, so Interlock read no peer’s checkout: peers’ work reached it only through what each agent pushed at Stop and the server’s record (V3.17.0). How this differs from real machines is under Limits.주차장 코드베이스(Python 90줄)의 시나리오 6개, 조건마다 10회씩 모두 180회이고, 2026-10-28 실행 전에 사전 등록했습니다. 그 전에는 어느 도구도 세트 Q에서 돌리지 않았습니다. 체크아웃마다 기계 이름과 Interlock 홈을 따로 두고, bare 저장소 하나가 팀의 git 원격 역할을 했습니다. 그래서 Interlock은 동료의 체크아웃을 읽지 않았고, 동료의 작업은 각 에이전트가 Stop에서 올린 것과 서버 기록으로만 닿았습니다(V3.17.0). 실제 여러 기계와 다른 점은 한계에 적었습니다.

Before set R, every run was on one machine세트 R 전에는 모든 실행이 한 기계였습니다

Set R (bikes, V3.16.0, 2026-10-28, pre-registered) was the first judged run across machines, simulated by turning Interlock’s pre-merge test off in every condition: Interlock 57/60, Shepherd 40/60, no tool 43/60, +28.3 points over Shepherd (95% CI +16.7 to +40.0), but Interlock lost R5 (8/10 against 10/10 for both), so by the pre-registered criteria it was not a win. In both R5 failures an agent’s test relied on renting twice at one station, which another agent’s new check refused; nobody was told, even by the rule Interlock used on one machine. V3.17.0 fixed this (the test’s writer is now told), and set R became its development set. The last set judged with all agents on one machine:세트 R(자전거, V3.16.0, 2026-10-28, 사전 등록)은 여러 기계 상황의 첫 판정 실행이었습니다. 모든 조건에서 Interlock의 병합 전 테스트를 꺼서 재현했고, 결과는 Interlock 57/60, Shepherd 40/60, 도구 없음 43/60으로 Shepherd보다 +28.3%p(95% 신뢰구간 +16.7~+40.0)였습니다. 하지만 R5에서 Interlock이 8/10으로 둘의 10/10에 졌기 때문에, 사전 등록 기준으로는 이기지 못했습니다. R5의 두 실패 모두 한 에이전트의 테스트가 같은 정거장에서 두 번 빌리는 데 기대고 있었는데, 다른 에이전트의 새 검사가 그것을 거부했습니다. 그런데 아무에게도 알리지 않았고, 한 기계에서 쓰던 규칙으로도 마찬가지였습니다. V3.17.0에서 고쳤고(이제 그 테스트를 쓴 에이전트에게 알립니다), 세트 R은 V3.17.0의 개발 세트가 됐습니다. 아래는 모든 에이전트가 한 기계에 있던 마지막 판정 세트입니다.

Where the gain comes from이득이 나오는 곳

The gain is concentrated in semantic conflicts: changes that merge cleanly as text but break another agent’s new code, such as a new required argument, a changed return type, a moved module or a renamed setting. With Shepherd and no tool there was often no failed merge to repair, so the break reached main. On independent features and edits to the same function all three conditions succeeded in every set from W to the last T run; across machines, Interlock lost R5 with V3.16.0, and no tool got 7/10 on Q5. Interlock catches the break before merging by sharing declared signatures and running tests on the state merged with teammates’ work, on another machine through the work each agent pushes at Stop (V3.17.0).이득은 의미 충돌에 몰려 있습니다. 텍스트로는 깨끗이 병합되지만 다른 에이전트의 새 코드를 깨뜨리는 변경, 곧 필수 인자 추가, 반환 타입 변경, 모듈 이동, 설정 이름 변경입니다. Shepherd와 도구 없음에서는 고칠 병합 실패가 없는 경우가 많아 깨진 채 main에 들어갔습니다. 독립 기능과 같은 함수 편집에서는 W부터 마지막 T 실행까지 모든 세트에서 세 조건 모두 성공했습니다. 여러 기계 상황에서는 V3.16.0의 Interlock이 R5를 졌고, 도구 없음은 Q5에서 7/10이었습니다. Interlock은 선언된 시그니처를 공유하고 동료 작업과 병합한 상태로 테스트해서, 병합 전에 깨짐을 잡습니다. 다른 기계의 동료와는 각 에이전트가 Stop에서 올린 작업으로 테스트합니다(V3.17.0).

Limits한계

  • Almost all runs use one model (Haiku 5.5). On Sonnet 5.5 (one set, 24 runs per condition) the gap nearly vanished. Opus, Codex, Cursor and OpenCode were not measured.거의 모든 실행이 모델 하나(Haiku 5.5)입니다. Sonnet 5.5(세트 하나, 조건당 24회)에서는 격차가 거의 사라졌습니다. Opus, Codex, Cursor, OpenCode는 재지 않았습니다.
  • Small Python projects (set L is the largest, with about 2,700 extra lines), six scenarios per set, 10 runs each. Every set from Y on repeats the same kinds of change (required argument, return type, module move, independent feature, same function, and either three agents or a setting rename) on a new codebase with new wording, and we designed them. Large real repositories and other languages were not tested.작은 Python 프로젝트(가장 큰 L은 약 2,700줄을 더함), 세트마다 시나리오 6개, 각 10회입니다. Y 이후의 모든 세트는 같은 종류의 변경(필수 인자, 반환 타입, 모듈 이동, 독립 기능, 같은 함수, 그리고 에이전트 3개 또는 설정 이름 변경)을 새 코드베이스와 새 문장으로 반복한 것이고, 우리가 설계했습니다. 실제 대형 저장소와 다른 언어는 재지 않았습니다.
  • Interlock’s time per turn is longer than Shepherd’s (4.6 s against 3.1 s on W); it finishes sooner because it needs fewer turns and fewer conflict-resolution sessions (none on W; on the last T run, 40 of 260 merges conflicted with Interlock against 133 with Shepherd).Interlock의 턴당 시간은 Shepherd보다 깁니다(W에서 4.6초 대 3.1초). 턴 수가 적고 충돌 해결 세션이 적어 더 일찍 끝납니다(W에서는 0회, 마지막 T 실행에서는 병합 260회 중 충돌이 Interlock 40회, Shepherd 133회).
  • Until set R every run had all agents on one machine, where Interlock also runs each agent’s tests merged with its peers’ work before the agent stops. With that test turned off (INTERLOCK_PREMERGE=0, set T, V3.15.1, run alone on 2026-10-28), Interlock finished 51/60, but only 3/10 on T3: when one agent moves a function to a new module, Interlock prevents the merge conflict that would otherwise send the merge to a resolver session, and the other agents’ imports of the old module break after merge. V3.16.0 made a moved or removed function a change the other agents must follow, through the store (T, test off: 59/60). Sets R and Q simulate separate machines on one: R by turning the test off in every condition (V3.16.0, not a win: R5 lost); Q by giving each checkout its own machine name and Interlock home, with a bare repository as the team’s remote, so that Interlock reaches peers’ work only through what each agent pushes at Stop (V3.17.0, a win). The checkouts still share git’s object store, so a fetch finds the commit already there; the server is a local SQLite file; network push and fetch times and failures are not reproduced. Real separate machines have not been tested.세트 R 전에는 모든 실행에서 에이전트가 한 기계에 있었고, Interlock은 에이전트가 끝내기 전에 동료 작업과 병합한 상태로 테스트를 돌립니다. 이 테스트를 끄면(INTERLOCK_PREMERGE=0, 세트 T, V3.15.1, 2026-10-28 단독 실행) Interlock은 51/60이었지만 T3에서는 3/10이었습니다. 한 에이전트가 함수를 새 모듈로 옮기면 Interlock이 병합 충돌을 막아 충돌 해결 세션이 열리지 않고, 다른 에이전트들이 옛 모듈을 import한 코드가 병합 후 깨집니다. V3.16.0부터는 함수의 이동·삭제를 저장소(서버)를 거쳐 다른 에이전트가 따라야 할 변경으로 다룹니다(T, 테스트 끔: 59/60). 세트 R과 Q는 한 기계에서 여러 기계를 재현했습니다. R은 모든 조건에서 이 테스트를 꺼서 재현했고(V3.16.0, R5를 져서 이기지 못함), Q는 체크아웃마다 기계 이름과 Interlock 홈을 따로 두고 bare 저장소를 팀 원격으로 써서, Interlock이 동료 작업에 각 에이전트가 Stop에서 올린 것으로만 닿게 했습니다(V3.17.0, 이김). 체크아웃들이 git 객체 저장소를 공유하므로 fetch할 때 커밋이 이미 있고, 서버는 로컬 SQLite 파일이며, 네트워크 push·fetch의 시간과 실패는 재현하지 않았습니다. 실제로 서로 다른 기계에서는 아직 시험하지 않았습니다.
  • Following the plan, each conflicting merge got one conflict-resolution session in every condition, which favors tools that do not block edits.계획서에 따라 모든 조건에서 충돌한 병합마다 충돌 해결 세션 1회를 허용했고, 이는 편집을 막지 않는 도구에 유리하게 작용합니다.
  • Scoring is by script (merge result, pytest, hidden checks), with no blinded human review. The hidden checks are not published so that the scenarios stay usable.평가는 스크립트(병합 결과, pytest, 숨겨진 검사)이고 사람의 블라인드 리뷰는 하지 않았습니다. 시나리오를 계속 쓰기 위해 숨겨진 검사는 공개하지 않습니다.
