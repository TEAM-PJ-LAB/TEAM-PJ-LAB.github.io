Interlock against Shepherd, pre-registeredInterlock 대 Shepherd, 사전 등록 비교

Real Claude Code agents work in parallel on a small codebase. We measure the share of tasks that end correctly merged and passing checks the agents never saw. Each time we changed Interlock after seeing results, we committed a new set of scenarios before running it. Earlier versions lost; the tables list every run, including the ones we set aside.실제 Claude Code 에이전트들이 작은 코드베이스에서 동시에 일합니다. 끝까지 올바르게 병합되고 에이전트가 보지 못한 검사까지 통과한 작업의 비율을 잽니다. 결과를 보고 Interlock을 고칠 때마다, 실행 전에 새 시나리오 세트를 커밋(사전 등록)한 뒤 다시 쟀습니다. 이전 버전은 졌고, 표에는 따로 분류한 실행까지 모든 실행을 실었습니다.

Where the gain comes from이득이 나오는 곳

The gain is concentrated in semantic conflicts: changes that merge cleanly as text but break another agent’s new code, such as a new required argument, a changed return type, a moved module or a renamed setting. With Shepherd and no tool there was often no failed merge to repair, so the break reached main. On independent features and edits to the same function all three conditions succeeded in every set from W onward. Interlock catches the break before merging by sharing declared signatures and running tests on the state merged with teammates’ work.이득은 의미 충돌에 몰려 있습니다. 텍스트로는 깨끗이 병합되지만 다른 에이전트의 새 코드를 깨뜨리는 변경, 곧 필수 인자 추가, 반환 타입 변경, 모듈 이동, 설정 이름 변경입니다. Shepherd와 도구 없음에서는 고칠 병합 실패가 없는 경우가 많아 깨진 채 main에 들어갔습니다. 독립 기능과 같은 함수 편집에서는 W 이후 모든 세트에서 세 조건 모두 성공했습니다. Interlock은 선언된 시그니처를 공유하고 동료 작업과 병합한 상태로 테스트해서, 병합 전에 깨짐을 잡습니다.

Limits한계

  • Almost all runs use one model (Haiku 5.5). On Sonnet 5.5 (one set, 24 runs per condition) the gap nearly vanished. Opus, Codex, Cursor and OpenCode were not measured.거의 모든 실행이 모델 하나(Haiku 5.5)입니다. Sonnet 5.5(세트 하나, 조건당 24회)에서는 격차가 거의 사라졌습니다. Opus, Codex, Cursor, OpenCode는 재지 않았습니다.
  • Small Python projects (set L is the largest, with about 2,700 extra lines), six scenarios per set, 10 runs each. Every set from Y on repeats the same kinds of change (required argument, return type, module move, independent feature, same function, and either three agents or a setting rename) on a new codebase with new wording, and we designed them. Large real repositories and other languages were not tested.작은 Python 프로젝트(가장 큰 L은 약 2,700줄을 더함), 세트마다 시나리오 6개, 각 10회입니다. Y 이후의 모든 세트는 같은 종류의 변경(필수 인자, 반환 타입, 모듈 이동, 독립 기능, 같은 함수, 그리고 에이전트 3개 또는 설정 이름 변경)을 새 코드베이스와 새 문장으로 반복한 것이고, 우리가 설계했습니다. 실제 대형 저장소와 다른 언어는 재지 않았습니다.

  • Every run had all agents on one machine, where Interlock also runs each agent’s tests merged with its peers’ work before the agent stops; that test cannot reach another developer’s machine. With it turned off (INTERLOCK_PREMERGE=0, set T, V3.15.1, run alone on 2026-10-28), Interlock finished 51/60, but only 3/10 on T3: when one agent moves a function to a new module, Interlock prevents the merge conflict that would otherwise send the merge to a resolver session, and the other agents’ imports of the old module break after merge. V3.16.0 makes a moved or removed function a change the other agents must follow, through the store and so on every machine: with the test still off it finished 59/60 and T3 10/10, and 60/60 with it on.
